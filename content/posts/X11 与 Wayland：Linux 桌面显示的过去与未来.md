如果你经常折腾 Linux 桌面，特别是平时习惯翻阅 Arch Wiki 来配置系统的玩家，对 X11 和 Wayland 这两个词绝对不陌生。在过去很长一段时间里，无论你使用的是 GNOME、KDE 还是像 i3wm 这样的平铺式窗口管理器，底层默默为你绘制出图形界面、接收你每一次鼠标点击的，都是一位年近四十的“老同志”——X Window System（通常被称为 X11）。

但最近这几年，社区的风向彻底变了。Ubuntu 早就切回了 Wayland，Fedora 更是激进地要在未来彻底剔除 X11 的支持，就连一直被视为“极其保守”的 Debian，也把默认会话交给了 Wayland。几乎所有主流的 Linux 发行版都在痛下决心，替换掉这个支撑了整个生态几十年的基石。要回答为什么会有这场浩大的底层大换血，我们得先看看 X11 究竟背负了多重的历史包袱。

### 满身补丁的 X11 巨兽

X11 诞生于上世纪 80 年代的 MIT Athena 项目。我们要理解它，就必须把自己代入到那个计算机算力极其昂贵的年代。当时 X11 在设计之初，最核心的理念是“网络透明性”。

在那时，研究员桌面上摆着的通常是只有显示器和输入设备的“瘦客户端”，而真正跑程序的怪物是机房里的大型机。所以 X11 被设计成了一个 C/S 架构的网络协议：你的电脑运行着 X Server（负责控制显示器和键盘），远端的大型机运行着 X Client（各种应用程序）。Client 会通过网络向 Server 发送“请在坐标 (x,y) 画一个红色矩形”这样的简单指令，Server 接收后在屏幕上绘制出来。

这个设计在当时简直是神来之笔，极其优雅。但也正是这份超前，为今天留下了几乎无法挽回的隐患。

随着个人 PC 算力的爆炸式跃升和独立显卡的普及，硬件生态发生了翻天覆地的变化。我们早就告别了依赖远端大型机算力的时代，现在几乎所有的图形渲染任务，都是在本地机器上直接完成的。现代的应用程序已经变得非常聪明且独立。借助 GTK、Qt 等强大的现代 UI 工具包，以及 OpenGL 或 Vulkan 这样的高级图形 API，应用程序会自己分配内存，并利用 GPU 的硬件加速能力，在幕后默默生成一幅包含高分辨率像素、阴影、半透明特效的完整画面。

理论上，既然画面已经画好了，直接递给底层显示硬件展示就行了。但这正是 X11 痛点的根源。

如果你去翻看如今 Xorg（X11 最流行的实现）的代码库，会发现 X11 最初的那些核心绘图指令早就被废弃了。为了适应现代桌面的需求，开发者们只能在这个古老的协议上不断打补丁：为了处理现代抗锯齿字体，有了 Xft；为了处理多显示器热插拔，有了 RandR 扩展；为了支持复杂的触摸板和多点触控，塞进去了 XInput。现在的 X11 就像一座摇摇欲坠的违建大楼，贴满了各种扩展补丁，代码库庞大且脆弱到几乎无人敢动。

![image](https://cdn.xuepoo.xyz/blog/posts/X11%20%E4%B8%8E%20Wayland%EF%BC%9ALinux%20%E6%A1%8C%E9%9D%A2%E6%98%BE%E7%A4%BA%E7%9A%84%E8%BF%87%E5%8E%BB%E4%B8%8E%E6%9C%AA%E6%9D%A5/Pasted%20image%2020260619005253.webp)

更荒谬的是它的渲染路径。当一个现代程序渲染好一帧画面后，它首先要把缓冲区告诉 X Server；X Server 拿到后不负责合成，而是发给一个叫 Compositor（合成器）的独立进程；Compositor 把所有窗口的画面叠加后，再还给 X Server；最后 X Server 才把它推送到显示器。这种中间人传话的模式不仅效率低下，而且极其容易在进程间同步时出现画面撕裂（Tearing）。

更为致命的是安全性。X11 设计之初是在受信任的学术网络里用的，根本没有“客户端隔离”的概念。任何一个跑在 X11 下的 GUI 程序，都可以毫无阻碍地监听全局的键盘事件、截取其他窗口的画面。这意味着，一个普通的计算器程序，在 X11 下天然就是一个极具破坏力的键盘记录器。这在如今充满恶意软件的互联网环境下，是不可接受的。

### Wayland：化繁为简的破局者

为了彻底解决这些历史遗留问题，Wayland 诞生了。值得澄清的是，Wayland 本身并不是一个类似于 Xorg 那样的巨大软件包，它**只是一个协议**，一个定义了显示服务器和客户端该如何用最有效率的方式沟通的标准。

Wayland 的核心思想极其简单：既然应用自己就能把画面渲染好，那我们就消除中间商赚差价。

![image](https://cdn.xuepoo.xyz/blog/posts/X11%20%E4%B8%8E%20Wayland%EF%BC%9ALinux%20%E6%A1%8C%E9%9D%A2%E6%98%BE%E7%A4%BA%E7%9A%84%E8%BF%87%E5%8E%BB%E4%B8%8E%E6%9C%AA%E6%9D%A5/Pasted%20image%2020260619005337.webp)

在 Wayland 的世界里，依赖的是 Linux 内核近年来完善的底层基础设施。比如负责直接与显卡打交道的 DRM（Direct Rendering Manager）和 KMS（Kernel Mode Setting），以及负责统一处理所有鼠标、键盘、触摸板输入的 libinput。

在这样的基建上，Wayland 架构去掉了独立的“显示服务器”角色。Compositor（比如 GNOME 的 Mutter 或者 KDE 的 KWin）本身就是显示服务器，也是窗口管理器。

![image](https://cdn.xuepoo.xyz/blog/posts/X11%20%E4%B8%8E%20Wayland%EF%BC%9ALinux%20%E6%A1%8C%E9%9D%A2%E6%98%BE%E7%A4%BA%E7%9A%84%E8%BF%87%E5%8E%BB%E4%B8%8E%E6%9C%AA%E6%9D%A5/Pasted%20image%2020260619005301.webp)

当一个应用程序渲染完一帧画面后，它会直接把这块内存的句柄丢给 Compositor。Compositor 直接读取这块显存，把所有窗口合成在一起，然后调用内核的 DRM 接口把画面刷到屏幕上。路径短了，画面撕裂的问题自然就迎刃而解了，这就让 Wayland 桌面的动画和拖拽体验能够做到极其丝滑（也就是常说的 “Every frame is perfect”）。

同时，Wayland 在安全性上做了一次彻底的重构。各个客户端之间是被严格隔离的，一个程序绝对无法直接读取另一个程序的输入或画面。这也让 Linux 桌面终于补齐了现代操作系统最基本的安全底线。

### 录屏危机与 PipeWire 的救场

强隔离虽然带来了安全，但在 Wayland 推出的早期，也引发了极其剧烈的阵痛——很多常用的软件突然全“瞎”了。

由于程序无法再像 X11 时代那样随意读取全局屏幕，导致所有的录屏软件（比如 OBS Studio）、视频会议软件（Zoom、Teams）、甚至是全局快捷键工具和取色器，在 Wayland 下全部失效，只能录到一片漆黑。这个问题一度让很多创作者对 Wayland 望而却步。

为了解决这个问题，社区并没有走回“开放后门”的老路，而是引入了一套非常优雅的现代机制：**XDG Desktop Portal** 和 **PipeWire**。

现在，当 OBS 想要录制屏幕时，它必须通过标准化的 D-Bus 接口向 XDG Desktop Portal 发起请求。这时，系统会弹出一个权限确认框，由**用户亲自决定**是否允许录屏，以及只分享哪个特定的窗口。一旦用户授权，底层的多媒体框架 PipeWire 就会在 Compositor 和 OBS 之间建立一条高效的、零拷贝的视频流通道。这套流程不仅性能极高，而且在逻辑上和 Android、macOS 的隐私授权机制完全一致。

### 旧时代的兼容与硬件厂商的妥协

当然，底层架构的推倒重来不可能一蹴而就。为了让海量的老旧软件平滑过渡，社区开发了 `XWayland`。这是一个极其巧妙的兼容层：它本质上是一个跑在 Wayland 内部的、没有自己显示输出的 X Server。它让那些传统的 X11 程序以为自己还活在 X 时代，从而能够毫无感知地在 Wayland 桌面里继续运行。

而在硬件方面，最大的阻力曾经来自于 NVIDIA。由于 N 卡早期固执地坚持使用自家的 EGLStreams 闭源方案，拒绝支持社区主推的 GBM 标准，导致很长一段时间内，Wayland 桌面在 N 卡上根本跑不起来或者毛病不断。这也是为什么 Linus Torvalds 曾经对着镜头给 NVIDIA 竖中指的原因之一。

好在最近几年，随着开源力量的倒逼以及 NVIDIA 态度的软化，他们终于开始在闭源驱动中全面拥抱 GBM 和 Explicit Sync（显式同步）等现代特性。今天，即便是拿着最新的 N 卡，运行像 Sway、Hyprland 这样极客的 Wayland 合成器，体验也已经非常顺畅了。

站在今天的时间节点回望，Wayland 已经熬过了最艰难的生态撕裂期。它不仅在技术架构上远超前辈，在生态上也已经全面成熟。X11 虽然还会作为底层的兼容层存在很长一段时间，但属于它的时代确实已经落幕。拥抱 Wayland，就是在拥抱 Linux 桌面的未来。
